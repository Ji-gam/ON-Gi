## 1. 스코프 경계 — 만들지 않는 것 [별첨 A]

기존 근무표 자동화 서비스(듀티플래너·듀티메이트·듀팅·하루듀티·AUTOSCHEDULE365)는 **경쟁자가 아니다.** 그들은 **근무표 안쪽**(누가 언제 일할지), 우리는 **근무표 바깥**(그 시간에 아이는 누가 보는지) — 후행 레이어다.

- **근무표 생성 기능은 만들지 않는다.** 사용자는 확정된 듀티표를 갖고 온다. 이 지점이 향후 API 제휴 포인트.
- 근무표 생성(Nurse Rostering Problem)은 NP-hard이고 학계는 CP-SAT로 접근한다. 5주 해커톤에서 과잉이며 **우리 문제는 그리디로 최적해가 보장되는 다른 문제**(§4.5)다. 이 구분을 밝히는 것이 기술 이해도의 증명이 된다.

## 2. 아동 연령과 법적 하드룰 [법률]

### 2.1 연령 밴드

| 밴드 | 연령 | 근거 |
|---|---|---|
| `INFANT` | 0~2세 (0~35개월) | 영아종일제 = 생후 3개월~36개월 |
| `TODDLER` | 3~5세 미취학 | 영유아보육법 = 만 6세 미만 취학 전 |
| `SCHOOL` | 6~12세 | 아이돌봄지원법 '아이' = 만 12세 이하 |
| 대상 외 | **만 13세 이상** | 스스로 돌봄 가능 → **아동 등록 불가** |

`children.birth_ym`만 저장하고 밴드는 **조회 시점 계산**(저장하면 시간이 지나 틀린다).

### 2.2 야간 인원 상한 (하드 필터)

교사:아동 비율 — **야간(22:00~06:00, 48슬롯 44~47+0~11)은 전 연령 1:5**, 주간은 `0세 1:3 / 1세 1:5 / 2세 1:7 / 3세 1:15 / 4세+ 1:20`.

혼합 연령은 **가장 엄격한 상한**(min). 랭킹 감점이 아니라 **Stage 1 배제 필터**. 야간 `INFANT`는 상한 이내여도 `HIGH_RISK` → 이행 확인 강화(§8.3).

### 2.3 야간 포인트 배율 금지

공공 요금(기본 12,180원/시, 야간 할증 50%)은 우리 가격 근거가 아니다. 야간 배율은 "야간 수당"으로 읽혀 C-1 리스크를 되살린다. 야간 기여는 `give_hours`와 신뢰 지표에만 반영.

## 3. 매칭 엔진 [별첨 B]

### 3.1 48슬롯 비트마스크

```
slot_index = hour * 2 + (1 if minute >= 30 else 0)      # 30분 단위 48슬롯
busy_mask BIT(48)   1 = 근무 중(돌봄 불가)
free_mask = ~busy & awake_mask                          # 조회 성능 위해 비정규화 저장
```

- `awake_mask`: 수면 보호 제외 슬롯(개인 설정)
- **N 근무(22:00~06:00) 종료 후 8슬롯(4시간)은 '수면 회복 구간'으로 자동 busy.** 없으면 "밤새 일하고 아침에 남의 아이를 보는" 후보가 상위로 올라온다 — 사고 위험이 가장 큰 조합. 기본값은 미결(Q-4)
- MySQL `BIT(48)` = 컬럼 하나, 비트 연산은 `int.bit_count()`로 상수 시간

### 3.2 상보성 — '겹침'이 아니라 '엇갈림'

```python
complement_ab = A.busy_mask & B.free_mask   # A는 근무인데 B는 가용 → 찾는 슬롯
complement_ba = B.busy_mask & A.free_mask
mutual = harmonic_mean(popcount(complement_ab), popcount(complement_ba))
```

조화평균이 곧 철학이다 — 한쪽만 봐주는 관계는 지속되지 않으므로 한쪽이 0이면 자동 배제된다. 지역 후보 축소는 **H3 인덱스 문자열 컬럼**으로(PostGIS 불필요).

### 3.3 Stage 1 — 하드 필터 + 태그 Set Cover

**하드 필터**(위반 시 배제): ① 반경 밖(§10) ② **야간 인원 상한**(§2.2) ③ 본인인증 미완료 / `confirmed_at IS NULL` 근무표 ④ 연령 밴드 미수용(`care_age_range`) ⑤ 필수 태그 미충족 ⑥ 단독위탁 요청인데 해당 관계 L3 미달(§7)

**필수 태그** = 폐쇄 어휘 10개(§3.3.1), 체크박스, Stage 1 하드 필터·Set Cover용. **선호 태그** = 개방 어휘, 자유 서술, 로컬 임베딩 소프트 점수 전용. 자유입력은 동의어가 난립해("야간가능"/"밤에 가능"/"나이트") 같은 의미의 두 태그가 서로를 덮지 못하므로, 하드 판정 어휘는 닫고 `tag_aliases`로 매핑한다.

**Set Cover** — `{야간가능, 알레르기대응, 차량보유, 초등저학년경험}`을 다 가진 이웃이 없으면 "필요 조건 전부를 덮는 최소 인원 조합"을 찾는다(NP-hard). `k ≤ 6 이고 C(m,3) ≤ 20,000`이면 **완전탐색(최적해 보장)**, 그 이상이면 greedy(미피복 태그를 가장 많이 덮는 후보, `O(m·k)`, `ln k` 근사).

**알고리즘을 과시하지 않는다**: 현재 규모에서 완전탐색이 더 빠르고 최적이다. greedy는 대비 경로이며, 근사해를 쓰면 **"최소 조합이 아닐 수 있음"을 UI에 표시**한다.

**사용자 주도 완화** [채팅] — Set Cover로도 조합이 안 되면 필수 태그를 하나씩 빼서 후보를 늘린다. 단 `skill_tags.category`로 통제: `SAFETY` **완화 불가(UI에서 해제 자체가 막혀야 한다)** / `CAPABILITY` 가능.

- 각 태그 제외 시 늘어나는 후보 수를 미리 표시("차량보유 제외 시 +7명"). 없으면 판단 근거가 없다. 후보 풀 1회 조회 후 **메모리 비트마스크 카운트**(조합마다 쿼리 N회보다 싸다)
- 완화 이력 로깅 → 자주 포기되는 태그가 사전 개선 데이터(Q-11)
- 다 빼도 0명이면 태그 문제가 아니라 **밀도 문제** → Pod 대기열(§9.1)로 안내

#### 3.3.1 필수 태그 사전 (10개)

**선별 기준**: ① 스키마가 이미 계산하는 것은 태그로 만들지 않는다(야간 가용=`free_mask`, 연령 수용=`care_age_range`, 거리=`h3_index`, 평판=`R`) ② 이진 판정 불가한 것은 선호로(하드 필터·피복 단위이므로) ③ "안 되면 아예 못 맡긴다"만 남긴다. → [별첨]의 ~30개를 10개로 축소.

| 카테고리 | 코드 | 라벨 | 비고 |
|---|---|---|---|
| `SAFETY`<br>(완화 불가) | `ALLERGY_CARE` | 알레르기 대응 (식이 제한 준수) | `children.allergies`와 교차 검사 하드 게이트 |
| | `MEDICATION` | 투약·기저질환 관리 | 실패 결과가 즉각적·비가역 |
| | `FIRST_AID` | 응급처치·심폐소생술 이수 | 야간 `INFANT`에서 사실상 전제 |
| | `SMOKE_FREE_HOME` | 흡연자 없는 가정 | 환경 조건 — 노력으로 안 바뀜 |
| `CAPABILITY`<br>(완화 가능) | `INFANT_CARE` | 영아(0~2세) 돌봄 경험 | `care_age_range`는 수용 *의사*, 이건 실제 *경험* |
| | `OVERNIGHT_OK` | 밤샘·숙박 돌봄 가능 | `free_mask`는 "비번이다", 이건 "밤새 데리고 잘 의사" |
| | `VEHICLE` | 차량 보유 (등하원·이동) | |
| | `MULTI_CHILD` | 형제·다자녀 동시 돌봄 | §2.2 인원 상한 연동 |
| | `HOME_HOSTING` | 내 집에서 돌봄 가능 | 구조적 분기 — 소프트 점수로 불가 |
| | `PET_FREE_HOME` | 반려동물 없는 환경 | 아동 조건에 따라 불필요할 수 있어 `CAPABILITY` |

`STYLE`(성실함·조용한 편 등)은 폐쇄 사전에서 **제외** → 선호 태그로.

**`SAFETY`는 사용자가 고르지 않고 아동 정보에서 자동 파생한다.** 완화 불가 태그를 부모가 직접 체크하게 하면 "혹시 모르니 다 체크"한 사용자가 사실상 매칭 불가가 된다. `children.allergies`가 있으면 `ALLERGY_CARE`가 자동 필수, 없으면 조건에 안 들어간다. `MEDICATION`도 동일. `FIRST_AID`의 야간 `INFANT` 자동 필수화는 미결(Q-17). `C(10,3)=120`으로 완전탐색 조건 여유.

### 3.4 Stage 2 — 소프트 점수 (0~100)

`S = 0.35·V + 0.25·M + 0.20·R + 0.20·B` — **V**(양육관 8문항 벡터 코사인 유사도, 만족) · **M**(§3.2 상보성 정규화, 지속) · **R**(완료 건수·태그 평판·노쇼율 **베이지안 평균**, 안전) · **B**(호혜 균형 §5.3, 네트워크 생존)

> **용어 확정 — "바움린드 8원칙"이라고 쓰지 않는다.** 바움린드(Baumrind)의 원 이론은 **온기(반응성)·통제(요구성) 2축**으로 양육 유형 넷을 분류한 것이고, **8개 원칙이라는 목록은 원전에 없다.** 우리의 8차원은 그 2축을 **각 4문항씩으로 조작화한 우리 설계**다. 문서·발표·위젯 모두 `바움린드 2축을 8문항으로 구성`으로 쓴다. 원전에 없는 이름을 붙이면 이론적 근거 전체가 의심받는다.
>
> **태그 10개(§3.3.1)와 8문항 벡터는 다른 층이다.** 태그는 **있냐 없냐**를 보는 Stage 1 하드 필터이고, 8문항은 **얼마나 비슷한가**를 재는 Stage 2 소프트 점수다. 한 층으로 그리면 "알레르기 대응이 유사도로 계산된다"로 읽혀 안전 설계가 무너져 보인다.

- **베이지안 평균이 신규 가입자 문제를 푼다** — 이력이 없으면 사전평균으로 수축되므로 0점 처리도 임의 대체도 불필요. [흐름]의 "별점 없는 신규 가입자" 딜레마 해법
- 가중치는 근거 없는 초기값. 관리자 조정 가능하게 두고 파일럿 튜닝(Q-12)
- **부스트는 `S`에 개입하지 않는다** — 별도 `sponsored` 슬롯. 점수에 돈이 섞이면 매칭 정확도라는 차별점이 무너진다

### 3.5 배정 — 의도적으로 타협한 지점

**긴급(T−2h 이내)** 은 즉시 최고점 이웃에게 푸시(지연이 곧 실패). **사전(T−24h 이상)** 은 **5분 배치 윈도우**로 모아 점수 내림차순 배정하고, **'도울 수 있는 요청이 1건뿐인 희소 이웃'을 우선 소비**해 인기 이웃 독점을 막는다.

**배정 그리디는 최적이 아님을 명시한다**(최적은 Hungarian). 그럼에도 택하는 이유: ① 5분 윈도우라 규모가 작다 ② "당신은 전체 최적을 위해 2순위와 매칭됐다"는 결과는 수용성을 무너뜨린다 ③ 완전 피복이 요구되지 않아 근사의 비용이 **아이가 혼자 남는 위험**으로 이어지지 않는다.

**일관된 축**: 릴레이는 최적성을 타협하지 않고, 배정은 의도적으로 타협한다. 기준은 알고리즘의 우아함이 아니라 **실패했을 때 아이에게 일어나는 일**이다.

### 3.6 릴레이 — 구간 피복의 최적 그리디

Activity Selection(겹치지 않는 구간 **개수 최대화**)에서는 EFT가 최적이지만, 우리 문제인 Interval Covering(목표 구간을 **빈틈 없이 전부 덮기**)에서는 **성립하지 않는다.**

```
반례) 목표 22:00~06:00 / n1=22:00~22:30, n2=22:00~02:00, n3=02:00~06:00
EFT : n1(22:30) 선택 → start>=22:30 조건에 n2 탈락 → n3 → {n1,n3}
      결과 22:30~02:00 3시간 30분 공백 → 아이가 혼자 남는다      정답: {n2,n3} 완전 피복
```

따라서 **'현재 커버 지점 이하에서 시작하는 구간 중 가장 멀리 뻗는 것'** 그리디를 채택. 최적성은 교환 논증, 복잡도 `O(N log N)`.

```python
def build_relay_chain(gap_start, gap_end, candidates):
    pool = sorted(candidates, key=lambda a: (a.start, -a.end))
    chain, covered, i, n = [], gap_start, 0, len(pool)
    while covered < gap_end:
        best = None
        while i < n and pool[i].start <= covered:      # 포인터 불역행 → 전체 O(N)
            c = pool[i]
            if best is None or (c.end, c.score) > (best.end, best.score): best = c
            i += 1
        if best is None or best.end <= covered:
            return None          # 이어받을 사람이 없다 → 릴레이가 끊긴다
        chain.append(best); covered = best.end
    return chain
```

- `None`은 실패가 아니라 **정직한 결과**다. 부분 체인 + 잔여 공백을 그대로 노출해야 부모가 다른 수를 쓴다. 억지로 채우면 아이가 혼자 남는 시간을 숨기는 셈
- **릴레이 인원 상한 2명 제안**(정서적 상한, Q-13). §2.2의 1:5와 **다른 축** — 하나는 어른 수, 하나는 아이 수

### 3.7 XAI — LLM 없이 근거 문장

각 항의 `(가중치 × 정규화 점수)`로 기여도를 계산해 **상위 2~3개만 템플릿에 주입**하는 결정론적 방식. 같은 입력에 같은 근거가 재현되고 외부 호출이 없어 응답 예산(§12.2)을 침범하지 않는다. LLM 후처리는 Tier B 선택 사항.
예: `"은주님이 야간(N) 근무인 22:00~06:00 중 6시간을 민준님이 비번(O)이에요"` / `"지난 3개월 상호 돌봄 4회, 주고받은 시간이 거의 같아요 (균형 지수 0.96)"`

### 3.8 반복 자동 매칭

고정 파트너 성립 시 근무표 주기로 다음 N주를 미리 생성하되 **확정하지 않는다**(`PROPOSED`). 근무표는 바뀌므로 확정은 양측 명시적 수락으로만. 변경 이벤트 → 영향 `PROPOSED` 무효화 + 재탐색. `feature.auto_rematch`로 분리(§10.4).

## 4. 근무표 인식 [별첨 B-7]

**3경로 — 전부 외부 API 불필요.** ① 엑셀·CSV: 셀 직접 읽기 ② 디지털 PDF: PyMuPDF **좌표 포함** 추출 → x/y 히스토그램 클러스터링으로 행·열 경계 추정 → 격자 복원 ③ 스캔 사진: 사진을 배경에 깔고 격자 정렬 **수동 입력 UI**(Tier C에서 자동화)

- **라벨 정규화는 사전 우선**: `{데이,이브닝,나이트,오프,○,●,/} → {D,E,N,O}`를 규칙 기반 사전이 처리, 사전에 없는 표기만 Tier B에서 LLM 위임
- PyMuPDF는 선행 프로젝트 사용 이력. 대안(Docling)은 **한글 OCR 글자 깨짐으로 배제한 검증 이력**이 있다
- 스캔을 수동 입력으로 두는 건 후퇴가 아니다 — 근무표를 잘못 읽으면 **없는 가용 시간이 생기고, 그 시간에 아이를 맡길 사람이 없다**

**검증 게이트**: 신뢰도 낮은 셀 → '확인 필요' 강제 확인 / 근무규칙 위반(N→D)·월 근무일수 이상치 → 경고 / **`confirmed_at` 이전에는 매칭 후보 진입 금지**

**돌봄 안전 정보(RAG)**: 공공기관 PDF/HTML을 PyMuPDF 추출·청킹 → Chroma 색인, `SQLRecordManager`로 증분 재색인. 질의는 `"생후 22개월 / 견과류 알레르기 / 야간 돌봄"` 형태. **Tier A는 생성 없이 원문 스니펫+출처만** — 아동 응급 정보에서 환각은 허용 불가이므로 열화된 대안이 아니라 **더 안전한 선택**이다.

## 5. 포인트와 호혜 균형 [별첨 B-5]

### 5.1 법적 성격 (§0.1 전제)

포인트는 **돌봄의 대가가 아닌 별도 보상점수**로, 시간과 고정 환율을 갖지 않는다. **환급·양도 불가**(가능하면 사실상 화폐가 되어 C-1 리스크 재발). **커머스 리워드는 `give_hours`에 가산하지 않는다.** UI·약관·코드에 "시급/수당/지급/정산" 금지.

### 5.2 원장 — 복식부기 append-only

```
point_ledger   -- UPDATE / DELETE 금지.  불변식: 동일 transaction_id 의 SUM(delta) = 0
  transaction_id UUID · profile_id · delta INT(음수=차감) · balance_after
  entry_type ENUM(welcome, care_earn, care_spend, escrow_hold, escrow_release,
                  escrow_refund, commerce_reward, penalty, adjust)
```

- **`SUM(delta)=0` 불변식**이 핵심. 웰컴·리워드처럼 상대가 없어 보이는 거래도 **시스템 계정을 상대편**으로 둔다. 없으면 포인트가 조용히 증발·창발한다. 정정은 반대 분개(`adjust`)로만, 행 잠금은 `SELECT ... FOR UPDATE`(InnoDB)
- `profiles.point_balance`는 **캐시** — 원장 집계와 대조하는 정합성 검증 배치가 C-7의 전제
- 에스크로: 수락 `escrow_hold` → 완료 `escrow_release` / 노쇼 `escrow_refund`, **24시간 자동 정산**

### 5.3 호혜 균형 B

```
ratio = give_hours / max(take_hours, 1)
B     = clip(ratio, 0, 2) * 50        # 1.0(균형)→50점, 2.0 이상→100점
take - give > 20h → 신규 요청 시 경고 배너 + 매칭 우선순위 하락
```

잔액에 **권리를 부여하지 않는다** — 한밭레츠가 20년간 겪은 플러스·마이너스 계정 불균형([유료])은 잔액에 권리가 붙을 때 재발한다. 20h 임계는 **차단이 아니라 경고+우선순위 하락**(끊으면 도움이 절실한 가구가 배제된다).

### 5.4 획득·소모

**획득** 웰컴(**본인인증 완료 시 계정당 1회** — 다중 계정 파밍 차단) / 프로필 100% 완성 / 돌봄 완료+상호 평가 / 용품 나눔 / 후기 작성(+3P) · **소모** 리뷰·상세 열람(−2P) / 부스트(10P/24h) / 반경 확장(§10.2)

- **재열람 무과금** — 같은 상대를 다시 볼 때마다 차감하면 이탈률 급증([흐름]). 열람과 제안을 분리 과금해 "정보만 보는 사용자"와 "매칭 의도가 있는 사용자"를 구분
- **균형 부등식**: `무료 획득 총량 ≥ 매칭 1건 성사 최소 포인트` — 회귀 테스트로 고정
- 유효기간 6~12개월, 만료 30일 전 고지. 웰컴 규모 미결(Q-1)

## 6. 돌봄마음 [채팅]

당근 온도(프로필 상시 노출 단일 숫자)를 **채택하지 않는다.** 리뷰에 별점을 달고 색으로 표현하며 이름은 **돌봄마음**이다.

| 평균 별점 | 0.0~0.9 | 1.0~1.9 | 2.0~2.9 | 3.0~3.9 | 4.0~4.9 | 5.0 |
|---|---|---|---|---|---|---|
| 색 | `RED` | `ORANGE` | `YELLOW` | `GREEN` | `BLUE` | `PINK` |

1. 별점은 **리뷰 작성 시 함께 입력**(별도 평가 화면 없음)
2. **프로필 상시 노출 안 함** — 아동 돌봄 맥락에서 낙인 효과가 크다
3. **리뷰 열람 시에만 함께 보인다**(열람은 포인트 소모 액션)
4. 누적 리뷰 임계 미만은 색 대신 "평가 누적 중"(Q-3)
5. 색은 **계산**(`mutual_rating_avg`만 저장). **색 단독 표현 금지** — 색+숫자+라벨 병기

**별점은 표시가 아니라 게이트다.** `mutual_rating_avg ≥ 4.0`이 **L3(단독위탁) 승급 조건**(§7)이고 `R`은 랭킹의 20%다. 4.0은 `BLUE` 경계와 정확히 겹치므로, 표시 규칙을 바꾸면 **승급 조건까지 흔들린다.**

미팅 안건: `5.0` 밴드가 한 점이라 리뷰 몇 건만 쌓이면 분홍이 사실상 안 나온다 — "만점 유지" 배지 의도면 유지, 상위 구간 표현 의도면 `4.5~5.0`(Q-10).

## 7. 신뢰 상태머신 [별첨 D] — 안전 핵심

```
[L0 미인증] → 본인인증 + 프로필·자녀정보 동의 → [L1]
[L1 인증]   열람·요청 가능, 단독위탁 불가 → 공개장소 공동육아 1회(양측 확인+일지) → [L2]
[L2 안면]   누적 1~2회 → 누적 3회 & 상호평점 ≥ 4.0 & 신고 0건 → [L3]
[L3 신뢰]   단독위탁 해금(해당 상대와의 관계에 한정) → 신고 접수 → [보류]
[보류]      24시간 검토 → 소명 → 기각: 이전 등급 복귀 / 인정: [정지]
[정지]      매칭 전면 차단
```

**신뢰는 사용자 속성이 아니라 관계(edge) 속성이다.** 프로필 컬럼으로 두면 "A와 3회 만난 사람이 처음 보는 B에게도 단독 위탁 가능"이 되어 안전장치가 완전히 붕괴한다.

```
trust_relations
  profile_a_id, profile_b_id      -- CHECK (a < b) 쌍 정규화, UNIQUE(a, b)
  level ENUM(L1, L2, L3, HOLD, SUSPENDED)
  completed_public_sessions INT, mutual_rating_avg NUMERIC(3,2)
  unlocked_solo_at TIMESTAMP NULL
```

- 등급 전이는 **서비스 레이어 단일 함수**만 수행 + `trust_transition_logs`(append-only). 비가역 안전 로직이므로 팀 합의 없이 변경 금지
- **`SUSPENDED`는 관계가 아니라 계정 단위**로 작동해야 한다. edge로 두면 정지된 사용자가 새 상대와 L1부터 다시 시작한다
- L1→L2의 "공개장소 공동육아 1회"는 부모 동석 세션 → **단독위탁은 반드시 대면 이력 위에서만 열린다.** [기술로직]의 "데려가기만 하고 돌보지 않는 경우"에 대한 1차 방어선

### 8.3 이행 확인 — "데려가고 돌보지 않는" 경우

**돌봄 일지(작성 의무)** + **랜덤 이행 확인**(무작위 시점 푸시 → 3택 + 한 줄) + **부모 주도 확인 요청**(횟수·간격 제한 후 푸시) + **체크인/아웃**(반경 충족 bool만, 좌표 미저장).

제한 초기값 `2시간당 1회 / 최대 3회 / 응답 15분`(Q-15) — 느슨하면 방치를 못 걸러내고 빡빡하면 감시받는 느낌으로 이탈한다. **단 심야 1회 제한은 아동 수면 보호 목적이므로 완화하지 않는다.** 야간 `INFANT`(`HIGH_RISK`) 강화도 이 제한과 충돌하면 수면 보호가 이긴다.

**1차 분쟁 판정은 자동화**(일지·확인 응답·시간 로그 규칙 판정), 사람은 자동 판정 불가 케이스만(24시간 검토 큐). 중재 인건비가 초기 비용의 핵심([흐름]). 학대 의심 신고 경로는 세션 화면 상시 노출 — 돌보는 부모는 사실상 신고의무자에 준하며 '즉시 조치 + 부모 연락 + 기록' 체계가 필요([법률]).

### 8.4 배상 책임

C2C 당사자 간 해결을 사전 합의서에 **명시**하고 플랫폼은 기록 제공자 위치에 선다. 보험 연계는 Phase 2이나 합의서 문안은 나중에 붙일 수 있는 구조로 미리 작성. **법률 검토 필요**: 부모 간 품앗이의 유사 알선업 해당 여부(Q-6).

## 9. 흐름과 Pod

### 9.1 Pod — 그룹 밀도 우선 [흐름 + 유료]

목표는 "규모·속도"가 아니라 **"그룹 밀도"** 다. 개인을 빠르게 많이 모으면 신규 가입자가 "주변에 아무도 없는 상태"를 경험하고 이탈한다.

- 구성 **4~6가구**. `PodRecruitment: OPEN(n/6) → FULL → ACTIVE`, 프로필 `WAITLISTED → POD_MEMBER`. 초반 Pod는 팀이 직접 조율 → **운영자 수동 개입 API 필요**
- **대기열 UX가 기능 요구사항**이다 — 가입 즉시 앱을 열어주지 않고 "그룹 모집 중 4/6가구" 진행률 표시. 콜드스타트 대응 로직이므로 상태 머신에 포함
- 종류: 지역 Pod(법정동+H3) / **직장 기반 Pod**(같은 직장·교대조 — 이미 아는 사이라 신뢰 형성 비용이 낮고 활성화가 빠름). 단 **회사가 홍보를 주도하지 않는다**(사생활 거부감) — 직장 정보는 후보 축소·가점만, 타인 노출 기본값 `off`

### 9.2 세션 상태 머신

```
PROPOSED →(수락) AGREED →(합의서+일정 확정) CONFIRMED[escrow_hold]
  →(체크인) IN_PROGRESS →(체크아웃+일지) COMPLETED[escrow_release] →(평가·별점) RATED
                                                          →(재만남 의사) FIXED_PARTNER → Pod
분기: PROPOSED→CLOSED(거절/만료) · CONFIRMED→NO_SHOW[escrow_refund] / CANCELLED
      COMPLETED→DISPUTED(이견, 일지·확인응답 기반 1차 자동판정)
```

포인트·`give_hours` 갱신은 **`RATED`** 시점(`COMPLETED`에서 주면 평가 미작성이 고착된다). 관계 등급 전이(§7)는 세션 상태와 별개 트랙.

## 10. 반경 기반 부분유료화 [유료]

무료/유료의 경계가 **기능이 아니라 반경**이다. **돌봄 교환 자체(핵심 가치)는 영구 무료**이고 반경 확장은 선택적 편의 기능이다.

### 10.1 반경 판정

기준은 **법정동 + H3 k-ring**(`profiles.h3_index` 문자열 컬럼, PostGIS 불필요). **정확한 좌표를 저장하지 않는다** — H3 셀 단위 저장으로 역추적 방지. 아동 거주지는 가장 민감한 정보다. 확정 전에는 "도보 N분" 수준만 표시.

### 10.2 단계형 확장 — 포인트를 더 쓰면 더 넓게

| 단계 | 범위 | 획득 경로 |
|---|---|---|
| `R0` | 800m~1km (도보 10분, TPL 기준) | 무료 기본 |
| `R1` | 2km | 포인트(소액) 또는 구독 |
| `R2` | 인접 행정동 | 포인트(고액) 또는 구독 |

`effective_radius()`는 구독자면 `R2` 고정, 아니면 `entitlements`의 `feature.radius_extend` 티어, 없으면 `R0`.

- **포인트 경로를 먼저 만든다**(결제 연동 불필요, MVP 즉시 가능). 현금은 PG 필요 → Phase 2
- 포인트 확장은 **기간제**(예: 7일). 영구 해금이면 [흐름]이 의도한 "활동 안 하면 포인트가 줄어드는 행동 유도 장치"가 무력화된다(Q-19)
- **`R2`는 반경이 아니라 행정동 집합** — k-ring으로 근사하면 경계와 어긋나므로 법정동 인접 리스트로 판정

**확장이 넓히지 못하는 것(어떤 등급에서도 불변)**: 야간 인원 상한 1:5 · `SAFETY` 태그 · L3 단독위탁 게이트 · 랭킹 `S` 순위(C-11) · **포인트 지급(C-10)**.

> C-10이 특히 중요하다. "구독하면 포인트도 준다"로 설계하면 **현금 → 포인트 → 돌봄 교환** 경로가 열려 포인트가 사실상 화폐가 된다. C-1에서 차단한 리스크가 뒷문으로 되살아난다.

### 10.3 비대칭 처리 — 발신자 기준 + 수신자에게 거리 명시 (확정)

**문제**: A가 `R2`로 확장하면 A는 무료 사용자 B를 보는데 B는 A를 못 본다. A가 요청을 보내면 B는 "설정 범위 밖 요청"을 받는다.

- 가) 상호 반경 교집합 → **기각.** 초기엔 대부분 무료라 반경을 넓혀도 매칭이 성립하지 않아 유료 기능이 작동하지 않는다
- **나) 발신자 기준 + 거리 명시 → 채택.** 유료 효용과 수신자 선택권을 동시에 보존
- 다) 발신자 기준, 표시 없음 → **기각.** 수락 후에야 거리를 알게 되어 노쇼·분쟁으로 되돌아온다

거리는 아동 돌봄에서 편의가 아니라 **실현 가능성** 문제다. 새벽 2시에 1.8km를 가야 한다는 사실은 **수락 전에** 알아야 한다. **동반 규칙: 긴급 요청(T−2h)은 반경 확장 대상에서 제외**(거리가 늘면 도착이 늦어져 넓은 반경이 실패율을 높인다).

**거리 구간 — 정확 거리 노출 금지.** "1.8km"를 반복 노출하면 여러 요청을 모아 위치를 삼각측량할 수 있다. API는 미터 값을 반환하지 않는다.

```
distance_band     ENUM(WALK, NEAR, ADJACENT)   -- 미터 값 반환 금지
out_of_my_range   BOOLEAN                      -- 수신자 기준으로 계산
```

`WALK`(~1km) = `도보 10분 거리` / `NEAR`(1~2km) = `약 2km 이내` / `ADJACENT`(2km~인접 행정동) = `인접 동 (차량 권장)`

**알림 문구 규격** — `out_of_my_range = true`면 **4곳 모두** 표시(한 곳이라도 빠지면 "수락 전에 알았다"가 성립하지 않는다).

| # | 지점 | 문구 |
|---|---|---|
| 1 | 푸시 | `민준님의 돌봄 요청 · 약 2km 이내 (내 설정 범위 밖)` |
| 2 | 목록 카드 | 배지 `범위 밖` + `약 2km 이내` |
| 3 | 상세 | `이 요청은 회원님이 설정한 동네 범위 밖에서 왔어요. 약 2km 이내예요.` |
| 4 | **수락 확인 모달** | `수락하면 약 2km 이동이 필요해요. 계속할까요?` — **확인 버튼 필수** |

**야간 가중 문구** — 22:00~06:00에 걸치고 범위 밖이면 모달(4)을 `심야(02:00) 돌봄이고, 약 2km 이동이 필요해요. 이동 시간을 포함해 도착 가능한지 확인해 주세요.`로 교체(밴드 계산은 불변, **문구만** 변경).

**금지**: 정확 거리·소수점·좌표·주소·역명 등 위치 특정 정보 / 재촉·압박 표현(`지금 바로`, `아무도 없어요`) — 거리 안내가 수락 압박 장치로 변질되면 안 된다 / 아이콘·색상 단독 표현(텍스트 병기 필수) / 모달 생략 구현

**로그**: `범위 밖` 요청의 수락률·노쇼율을 별도 집계 — 나) 안이 실제로 작동하는지 검증하는 지표. 노쇼율이 유의하게 높으면 `ADJACENT` 밴드 자체를 재검토한다.

### 10.4 유료 전환 지점의 기능 분리

결제 로직은 넣지 않되 처음부터 **독립 권한 체크로 감싼다**([흐름]).

`feature.radius_extend`(포인트로만, 기간제) · `feature.detail_view`(포인트 차감) · `feature.advanced_filter`(육아방식·부모 연령대 등 세부 필터, **전원 허용**) · `feature.boost`(포인트 차감) · `feature.auto_rematch`(전원 허용) · `feature.partner_coupon`(미구현, Phase 2)

- 판정은 **`entitlement` 서비스 한 곳**에 모은다. 각 API가 개별적으로 "구독자인가"를 물으면 Phase 2에서 전부 뜯어야 한다
- **세부 필터는 Tier A 전원 허용** — 파일럿 규모(250명)에서 필터를 잠그면 매칭 성공률 20% 달성 자체가 어렵다. 스위치는 열어두되 켜지 않는다
- 무료 티어 수익원은 **없다**(트래픽 확보 + 신뢰 데이터 축적). [유료]의 손익 시뮬레이션이 이 전제로 계산됐다

### 10.5 구독료 — 월 1,990원 (확정)

**제공**: `R2` + 세부 필터 + `sponsored` 슬롯. **제공 안 함**: 포인트(C-10), 랭킹 개입(C-11), 안전 게이트 완화. 결제는 PG 필요 → Phase 2. 단일 요금제로 둔다 — 티어가 여러 개면 무료 사용자가 "나는 몇 등급인가"를 계산하기 시작하고, 돌봄 커뮤니티에서 그 감각은 신뢰를 깎는다.

**[유료]의 12개월 손익을 1,990원으로 재계산해야 한다**(Q-18). 전환율 5%는 [유료]가 "검증 안 된 추정치"로 표시한 값이고 **가격을 올리면 전환율도 떨어질 수 있어 매출을 2배로 단순 계산하면 안 된다.** 부분유료화는 안전마진을 키우는 장치이지 성장 실패를 구원하지 못하며, 6개월차 Go/No-Go의 중요성은 그대로다.

**설계 제약: 전량 로컬 실행 — 외부 API 키 0개.** 데모가 네트워크·키 발급에 의존하지 않는다. 단 로컬 모델은 최초 ~2GB 다운로드, 서빙 ~1.1GB 상주 → 데모 노트북 사양 확인(Q-14).

### 12.2 성능 예산 (P95 3초 목표 / T-QUAL-1)

`POST /matches/search` **목표 P95 800ms** = H3 k-ring 조회 50ms + 비트마스크 교차 30ms + 코사인 20ms + 평판·원장 집계 100ms(캐시) + 직렬화·근거 문장 50ms. 근무표 파싱·안전 정보 색인은 Celery 비동기로 요청 경로 예산에서 제외.

근거 문장에 LLM을 쓰지 않는 것이 예산을 지킨다(§3.7). 평판 집계 100ms가 캐시 전제이므로 `point_balance` 캐시(C-7)는 성능 요구에서 나온 것이고, 정합성 검증 배치가 그 대가다.

## 13. 개발 우선순위

> 가설 검증 관점의 단계 구성·지표·반증 조건은 [HYPOTHESIS_ROADMAP.md](HYPOTHESIS_ROADMAP.md) 참조. P0=1단계, P0 후반~P1=2단계, P1=3단계에 대응한다.

[유료]의 Go/No-Go(6개월차: 가입자 250명, 매칭성공률 20%)를 역산 — **"완결된 Pod 사례 1개"** 가 목표.

**P0 (Pod 하나 완결 최소 경로)**: ① 프로필+아동 등록+부모 동의 ② 근무표 업로드→엑셀/PDF 파싱→검증 게이트→`confirmed_at` ③ 48슬롯 마스크+수면 회복 구간 ④ Stage 1 하드 필터(반경·**야간 상한**·필수 태그) ⑤ Stage 2 점수+XAI 근거 문장 ⑥ 요청→수락→에스크로 홀드→확정 ⑦ 체크인/아웃+**일지(의무)** ⑧ 리뷰+별점→돌봄마음+포인트 원장 ⑨ **신뢰 상태머신 L1→L2→L3(단독위탁 게이트)** — 안전 핵심이라 뺄 수 없다 ⑩ Pod 대기열+운영자 수동 조율 API

**P1**: 릴레이 체인+잔여 공백 · Set Cover 완전탐색+태그 완화+후보 수 미리보기 · 5분 배치/긴급 분기 · 랜덤 이행 확인+부모 주도 확인 · 안전 정보 RAG(스니펫만) · 반경 확장 포인트 경로+거리 밴드 알림 · 원장 정합성 배치 · 반복 자동 매칭 · 신고 검토 큐+1차 자동 판정

## 15. 코드에 강제하는 규칙 (리뷰 체크리스트)

**법·안전 (타협 불가)**
1. 야간(22:00~06:00) 인원 상한 **1:5는 배제 필터**, 랭킹 감점 아님 (§2.2)
2. 만 13세 이상 아동 등록 불가. 연령 밴드는 `birth_ym`에서 **계산**(저장 금지) (§2.1)
3. **신뢰 등급은 `profiles` 컬럼 금지 — `trust_relations`(edge)**. 단독위탁은 해당 관계 L3에서만. 전이는 서비스 레이어 **단일 함수** + append-only 로그, 팀 합의 없이 변경 금지. `SUSPENDED`는 **계정 단위**(edge면 새 상대와 L1 재시작 가능) (§7)
4. `SAFETY` 태그는 완화 대상 제외 — **UI에서 해제 자체가 불가능**해야 한다 (§3.3)
5. 아동 정보: 암호화 + 접근 로그 + 법정대리인 동의 선행, 매칭 확정 상대에게만 노출 (§8.2)
6. 좌표 미저장(H3 셀 단위). 체크인은 반경 충족 bool만. 거리는 **`distance_band` enum만** 반환(삼각측량 방지) (§10.1, §10.3)
7. 심야 이행 확인 1회 제한 완화 금지. 돌봄 일지는 **의무** (§8.3)

**포인트·평가**
8. 포인트에 시간 환율 부여 금지. 환급·양도 API 금지. 커머스 리워드는 `give_hours` 가산 금지 (§5.1 — Q-0 확정 대기)
9. `point_ledger` **`UPDATE`/`DELETE` 금지**, 동일 `transaction_id`의 `SUM(delta)=0`. 정정은 반대 분개. `point_balance`는 캐시(원장이 원천) + 정합성 검증 배치 (§5.2)
10. 호혜 균형 잔액에 **권리 부여 금지**. 20h 초과는 차단 아니라 경고+우선순위 하락 (§5.3)
11. 돌봄마음 색상은 계산(저장 금지), 프로필 상시 노출 금지, 색 단독 표현 금지. `mutual_rating_avg`는 **L3 게이트 입력**이므로 표시 규칙 변경 시 승급 조건 영향 확인 (§6)
12. 무료 획득 총량 ≥ 매칭 1건 최소 소요 포인트 (테스트로 고정) (§5.4)

**알고리즘·구조**
13. 릴레이는 **EFT 금지** — 반례 테스트를 먼저 작성(TDD). 끊김은 `None`으로 정직하게 반환하고 부분 체인+잔여 공백 노출, 억지 피복 금지 (§3.6)
14. Set Cover greedy 사용 시 **"최소 조합이 아닐 수 있음" UI 표시** (§3.3)
15. `confirmed_at IS NULL` 근무표는 매칭 후보 진입 금지. 근무표 **생성 기능 만들지 않는다** (§1, §4)
16. Tier A에서 LLM 사용 금지 — 안전 정보는 **원문 스니펫+출처**, 근거 문장은 템플릿(성능 예산 근거) (§3.7, §4, §12.2)
17. 부스트는 `S`에 개입하지 않는다 — 별도 `sponsored` 슬롯 (§3.4)

**유료화**
18. 유료 전환 지점은 `entitlement` **단일 지점**에서 판정 (§10.4)
19. **구독·결제는 포인트를 지급하지 않는다** — 현금→포인트 경로 금지 (C-10)
20. 반경 확장은 후보 풀 크기만 바꾼다 — 야간 상한·`SAFETY`·L3 게이트·랭킹 순위 불변. 긴급 요청(T−2h)은 확장 대상 제외 (§10.2, §10.3)
21. `out_of_my_range = true`면 푸시·목록·상세·**수락 확인 모달 4곳 모두** 표시(모달 생략 금지). 재촉·압박 표현 및 아이콘/색상 단독 표현 금지 (§10.3)
