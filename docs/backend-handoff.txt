[ 확정된 정책 결정 3가지 ]

 1. 노쇼 방지금 = 포인트로 진행 (현금/PG 아님)
    - Figma 목업에는 "노쇼방지금 20,000원"으로 그려져 있으나 현금 결제는 채택하지 않음
    - 근거: 기획서에 현금 보증금/예치 개념 없음, 요구사항정의서에서 에스크로·PG는 P1 제외,
            화면명세서 v2에서 "노쇼 2만 원 결제 화면: 없음"으로 명시 삭제됨
    - 즉 기존 PointHold(슬롯 단위 포인트 홀드) 방식을 그대로 사용
    - 화면 문구는 포인트 기준으로 프론트에서 수정 예정

 2. 첫 접촉 = 공동육아(첫 만남)로 진행
    - 사용자 여정: 추천 → 궁합 상세 → "첫 만남 요청" → 공개장소 공동육아 3회 → L3 → 단독 돌봄

 3. 양육 가치관 = 8축으로 진행
    - 목업의 레이더 차트 8축: 규칙과 자율 / 식습관 / 놀이·학습 / 감정 표현 /
                              미디어 사용 / 훈육 방식 / 안전 기준 / 또래 관계

------------------------------------------------------------------------
 A. 위 결정에 따라 백엔드 수정이 필요한 항목 (프론트 우회 불가)
------------------------------------------------------------------------

 A-1. [필수] 공동육아를 관계 생성의 시작점으로 허용
      현재: app/services/trust_level_service.py::schedule_joint_session()이
            관계(TrustRelationship)가 없으면 404로 거부.
            에러 메시지: "매칭 관계가 없습니다. 먼저 돌봄 요청을 주고받으세요."
            즉 관계는 care_session accept 시 grant_l1()으로만 생성됨.
      요청: 공동육아 일정 등록(첫 만남 요청) 시점에 관계가 없으면 L1을 생성하도록 변경.
            또는 "첫 만남 요청 → 수락" 엔드포인트를 신설하고 수락 시 L1 부여.
      영향: 이게 없으면 목업의 사용자 여정 자체가 성립하지 않음. 최우선.

 A-2. [필수] 양육 가치관 8축 저장
      현재: ParentingValues에 warmth_score / control_score 2축 집계값만 저장.
            8문항 개별 응답은 저장되지 않아 레이더 차트를 그릴 수 없음.
      요청: 8문항 개별 응답값 보관 + 축별 라벨 제공.
            매칭 후보 응답(CandidateResponse)에 상대의 8축 값도 포함 필요
            (내 값과 겹쳐 그려야 하므로).
      관련 화면: 궁합 상세(레이더 차트) — 3개 화면에 반복 등장.

 A-3. [필수] L3 승급 조건에 평점 조건 추가
      현재: joint_session_count >= required 만 확인.
      목업: "공개 장소에서 3회를 함께 돌봤고, 서로의 평가가 모두 4.0 이상입니다"
      요청: 양측 상호 평점 평균 4.0 이상 조건 추가.

 A-4. [필수] 공동육아 회차별 상호 평가
      현재: confirm_joint_session()은 boolean 확인만. 평가(rating)는 CareSession에만 붙음.
      목업: "회차마다 서로 평가를 남기고, 두 사람 모두 제출해야 기록으로 인정됩니다"
      요청: JointCareSession에도 상호 평가 제출 API 필요.

 A-5. [중요] 공동육아 기록 필드 확장
      현재: JointCareSession = place, scheduled_date, confirmed_by_*, status
      목업: "1회차 · 망원한강공원 / 7월 12일 · 2시간 · 양가 부모 모두 동석"
      요청: 소요 시간, 메모(한 줄 설명) 필드 추가.

 A-6. [중요] 돌봄 세션 상태에 중간 단계 추가
      현재: REQUESTED → CONFIRMED (수락 즉시 확정, 홀드 자동 생성)
      목업: PROPOSED → (수락) AGREED → (양측 예치·동의) CONFIRMED
      요청: AGREED 상태 + "약속이행 규칙 동의" 기록 + 양측 예치 완료 여부 필드.
            ※ 예치는 포인트로 진행(결정 1). 현재 홀드는 요청자 한쪽만 잡히는데,
              목업은 양쪽 예치이므로 양측 홀드로 바꿀지 확인 필요.

------------------------------------------------------------------------
 B. 백엔드에 아예 없는 신규 기능
------------------------------------------------------------------------

 B-1. [핵심] 돌봄 사각지대 자동 계산
      근무표 등록 시 "월·목 07:00-09:00 등원 전 / 화·금 17:00-19:00 하원 후"를 자동 도출.
      - 내 근무 시간 중 아이를 맡길 사람이 없는 구간을 계산
      - "등원 전 / 하원 후" 판정을 위해 어린이집/보육시설 이용 시간대(예: 09-17) 입력 필요
      - 사각지대 기준 역방향 매칭("사각지대 메울 이웃 찾기")
      기획서상 이 서비스의 핵심 차별점이므로 우선순위 높음.

 B-2. [핵심] "이제 커버되는 시간" 타임라인 집계
      여러 이웃 조합으로 하루가 채워지는 뷰
      (07-09 태호님 등원동행 / 09-17 어린이집 / 17-19 태호님 하원후 / 주말 서연님 단독위탁)

 B-3. [중요] 누적 통계 집계 API
      "누적 돌봄 4회 (받은 6시간·준 5시간)", "단독 위탁 이력 1회", "받은 평점 4.6→4.7"
      현재 집계 엔드포인트 없음. is_solo/actual_minutes로 계산은 가능하나 API 필요.

 B-4. [중요] 사진 업로드 인프라
      돌봄일지 사진(2칸, "30일 후 자동 삭제"), 평가 화면 사진, 프로필 사진
      현재 파일 업로드 엔드포인트·스토리지·모델 필드 전무.
      ※ 요구사항 REQ-F-CAR-04(안심 사진)이 "중요"로 정의돼 있으나 미구현 상태.

 B-5. [중요] 매칭 필터 파라미터
      GET /mat/candidates에 필터 없음. 목업 필터 항목:
      - 돌봄 시간대(평일저녁/평일오전/주말/야간/등하원) 중복선택
      - 아이 나이(0-2/3-5/6-8/9세이상)
      - 양육 성향(규칙/자율/미디어최소화/바깥놀이/책읽기/식단관리)
      - 안전·신뢰(L2이상/L3단독위탁가능/비흡연/반려동물없음)
      - 거리 슬라이더(도보 5~20분)
      추가 요청: "태그 N개를 걸면 후보가 M명까지 줄어듭니다" 안내를 위해
                필터 적용 전후 후보 수를 함께 반환.

 B-6. [보통] 매칭 근거에 알레르기 경험 추가
      목업: "유제품 알레르기 아동을 돌본 경험이 있습니다"
      현재 build_recommendation_reason()은 거리·상보·가치관·신뢰 4가지만 사용.
      과거 돌봄 이력에서 알레르기 대응 경험을 추출하는 로직 필요.

 B-7. [보통] 포인트 적립 규칙 정의
      목업: 2시간 돌봄 → "+12P (2시간·웰컴보너스 포함)"
      현재: 2시간 = 4슬롯 → +4P. 웰컴보너스 개념 없음.
      요청: 적립 배수/보너스 정책 확정 (숫자가 목업과 안 맞음).

 B-8. [보통] 상세정보 유료 열람 (2P 차감)
      목업: "상세정보를 열람하면 2P가 차감됩니다 / 열람 기록은 상대에게 남지 않습니다"
      근무표 상세·아이 특성·받은 리뷰 전체를 포인트 차감 후 공개.
      현재 해당 개념 없음.

 B-9. [보통] Pod 도메인 전체
      목업에 Pod 탭 + Pod 상세(모집 현황 4/6가구, OPEN→FULL→ACTIVE 진행바,
      "8월 6일쯤 6가구가 채워질 것으로 보입니다" 예측, 참여 이웃 목록, 가입 신청) 존재.
      현재 데이터 모델만 준비되고 API 없음(기획서상 MVP 이후 범위).

 B-10. [보통] 신고 도메인
      모든 화면 우상단 "신고" 버튼. 현재 신고 도메인 미구현이라
      trust_level_service의 강등도 운영자 수동 처리 상태.

 B-11. [확인 필요] 돌봄일지 태그 필드
      현재: meal/sleep/mood/note/allergy_note 전부 자유 문자열.
      목업: 기분 3단 선택 + 기록 태그 5개(간식 먹었어요/낮잠 없음/바깥 놀이/투약/다툼)
      요청: 태그 배열을 담을 필드 추가 또는 기존 필드 용도 합의.

 B-12. [확인 필요] "일지 미작성 시 정산 보류"
      목업 문구: "일지를 작성하지 않으면 노쇼방지금 정산이 보류됩니다"
      해당 게이트가 실제로 구현돼 있는지 확인 필요.
      (신뢰 가중치 w4에 '일지 작성률'은 존재)

 B-14. [필수] 공동육아 목록 조회 API 부재
      현재 trs_routers.py에 공동육아 조회용 GET이 없음.
      (POST 생성 / POST 확인 / GET 관계(횟수만) 만 존재)
      목업의 "함께한 기록"(1회차 망원한강공원 · 2회차 마포어린이도서관 · 3회차 …) 목록을
      그릴 수 없음. 관계별 공동육아 목록 조회 API 필요.
      예: GET /trs/relationships/{other_user_id}/joint-sessions

 B-13. [확인 필요] 사용자 닉네임 조회 API
      현재 상대 닉네임을 얻을 방법이 매칭 후보 목록뿐이라, 후보에서 빠진 상대는
      이름을 표시할 수 없음(진행중 돌봄/채팅 목록 등에서 문제).
      GET /users/{id} 같은 최소 공개 프로필 조회 필요.
